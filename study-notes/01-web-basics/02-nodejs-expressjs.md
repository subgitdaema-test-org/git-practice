## 1. Node.js

**정의:** 브라우저 밖에서 JavaScript를 실행 가능하게 하는 런타임(V8 엔진 + 이벤트 루프 기반 비동기 I/O 시스템), 언어가 아닌 실행 환경

**등장 배경**
- 프론트엔드(JS)와 백엔드(Java/PHP/Python 등) 언어 이원화로 인한 컨텍스트 스위칭 비용 발생
- 기존 서버의 요청당 스레드 할당 방식(블로킹 I/O) → I/O 대기 중 자원 낭비 심화
- Ryan Dahl, 크롬 V8 엔진 + 비동기 I/O 결합 → 싱글 스레드 기반 대량 동시 연결 처리 런타임 고안

**핵심 아키텍처**

| 구성 요소 | 역할 |
|---|---|
| 싱글 스레드 이벤트 루프 | 코드 실행 자체는 한 스레드에서 담당 |
| 논블로킹 I/O | 시간 소요 작업은 libuv 스레드 풀에 위임 |
| 콜백 / Promise / async-await | 비동기 작업 완료 시점의 처리 방식 지정 |

> **주의:** 멀티스레드 아님, CPU 집약적 연산에는 불리 → I/O 중심 워크로드(API 서버, 실시간 통신)에 적합

**실무에서의 형태**

| 사용처 | 설명 |
|---|---|
| API 서버 | Express, Fastify, NestJS 기반 REST/GraphQL 백엔드 |
| 패키지 생태계 | npm을 통한 방대한 오픈소스 모듈 즉시 활용 |
| 빌드 툴체인 | Webpack, Vite, Babel 등 프론트엔드 빌드 도구의 실행 기반 |
| 실시간 서비스 | Socket.io 기반 채팅, 알림, 협업 도구 |
| BFF | 프론트엔드 팀의 자체 중간 서버 레이어 구축 |

**인과관계 요약**
> 언어 이원화 및 블로킹 I/O의 비효율 → V8 엔진 + 비동기 I/O 결합한 런타임 등장 → 싱글 스레드로 대량 동시 처리 가능 → JS 풀스택 개발 및 I/O 중심 서비스 생태계 형성

## 2. Express.js, package.json, PM2

**정의**

| 용어 | 의미 |
|---|---|
| Express.js | Node의 http 모듈 위에서 라우팅·미들웨어를 선언적으로 다루는 경량 웹 프레임워크 |
| package.json | 프로젝트의 이름·버전·의존성·실행 스크립트를 선언한 메타데이터 파일 |
| PM2 | Node 프로세스의 크래시 감지·자동 재시작·클러스터링을 담당하는 프로세스 매니저 |

**등장 배경**
- 순수 Node http 모듈 사용 시 라우팅·메서드 분기 전량 수동 처리 → 코드 비대화
- TJ Holowaychuk, 라우팅·미들웨어 체이닝의 선언적 추상화 계층으로 Express 고안(2010)
- 프로젝트별 의존성·버전 관리 필요성 → npm 등장과 함께 package.json 표준화
- Node 싱글 스레드 특성상 미처리 예외 발생 시 프로세스 전체 종료 위험 → 자동 재시작 도구(PM2) 필요성 대두

**핵심 개념**

| 개념 | 설명 |
|---|---|
| 라우팅 | `app.get()`, `app.post()` 등 메서드 기반 요청 경로 처리 |
| 미들웨어 | `(req, res, next)` 형태의 요청-응답 파이프라인 처리 함수 |
| dependencies / devDependencies | 프로덕션 필수 패키지 / 개발 전용 패키지 구분 |
| package-lock.json | 실제 설치된 정확한 버전 고정 |

**실무에서의 형태**

| 사용처 | 설명 |
|---|---|
| REST API 기본 프레임워크 | 인증(passport), 로깅(morgan), CORS 등 미들웨어 조합 |
| 팀 표준 명령어 | `npm run dev`, `npm run build`, `npm test` |
| 온보딩 표준 절차 | `git clone` → `npm install` → `npm run dev` |
| 컨테이너 환경 논쟁 | K8s 오케스트레이터와 PM2의 역할 중복 이슈 |

**인과관계 요약**
> http 모듈의 반복적 분기 처리 부담 → 선언적 라우팅·미들웨어 프레임워크(Express) 등장 → 외부 패키지 조합 개발 방식 확산 → 의존성 관리 표준(package.json) 필요 → 싱글 스레드의 프로세스 종료 리스크 → 자동 재시작 도구(PM2) 등장

## 3. Express.js 설치

**정의:** npm을 통해 Express 패키지를 프로젝트에 다운로드하고, package.json/package-lock.json에 의존성으로 기록하는 절차

**등장 배경**
- Node 코어 경량화 철학 → 필요 기능은 외부 패키지로 확장하는 생태계 구조
- Express, 내장 기능이 아닌 별도 설치 필요한 외부 패키지로 위치

**설치 절차**

| 단계 | 명령어 | 의미 |
|---|---|---|
| ① 프로젝트 폴더 생성 | `mkdir`, `cd` | 작업 디렉토리 준비 |
| ② package.json 생성 | `npm init -y` | npm 프로젝트로 선언 |
| ③ Express 설치 | `npm install express` | node_modules 설치 + package.json 자동 기록 |
| ④ 서버 작성·실행 | `app.js` 작성 후 `node app.js` | 라우트 정의 및 서버 구동 |

**핵심 원칙**

| 원칙 | 이유 |
|---|---|
| node_modules는 git 커밋 금지 | 용량 문제, package.json/lock으로 복원 가능 |
| `--save-dev`(devDependencies) 구분 | 프로덕션 배포 시 불필요한 개발 도구 제외 |
| CI 환경에서 `npm ci` 사용 | lock 파일 기준 정확한 버전만 설치, 드리프트 방지 |
| `^`(caret) 버전 표기 | 메이저 버전 고정, 마이너·패치는 유동적 허용 |

**실무에서의 형태**

| 사용처 | 설명 |
|---|---|
| .gitignore 설정 | node_modules 제외 표준 관행 |
| nodemon 병행 설치 | 파일 저장 시 자동 서버 재시작 |
| CI/CD 파이프라인 | `npm ci`로 정확한 버전 재현 |

**인과관계 요약**
> Node의 경량 코어 철학 → Express의 별도 설치 필요성 → npm init/install을 통한 의존성 선언 및 설치 → package.json(의도)과 package-lock.json(고정)의 역할 분리 → 팀 전체 동일 환경 재현 가능

## 4. 코드 컨벤션

**정의:** 들여쓰기, 네이밍, 세미콜론 등 코드 작성 스타일을 팀 단위로 통일한 규칙 체계

**등장 배경**
- 코드의 작성 시간보다 읽히는 시간이 압도적으로 긴 특성
- JavaScript 문법의 높은 유연성(세미콜론 생략, var/let/const 혼재 등) → 개발자별 스타일 편차 심화
- 다수 개발자 협업 시 스타일 차이 → 지저분한 diff, 코드 리뷰 시간의 비효율적 소모

**핵심 구성 요소**

| 층위 | 내용 | 담당 도구 |
|---|---|---|
| 포매팅 규칙 | 들여쓰기, 줄바꿈, 세미콜론, 따옴표 등 | Prettier |
| 네이밍/구조 규칙 | camelCase, PascalCase, UPPER_SNAKE_CASE 등 | ESLint |

**실무에서의 형태**

| 사용처 | 설명 |
|---|---|
| ESLint | 잠재적 버그 패턴 정적 분석(미사용 변수, `==` 사용 등) |
| Prettier | 저장/커밋 시 형식 자동 통일 |
| Husky + lint-staged | 커밋 직전 자동 린트·포맷 실행 |
| CI lint 단계 | PR 시 자동 검사, 실패 시 머지 차단 |
| 스타일 가이드 준수 | Airbnb, Google 등 팀 표준 채택 |

**인과관계 요약**
> JS 문법의 유연성 → 개발자별 스타일 편차 발생 → 협업 시 diff 오염 및 리뷰 비효율 초래 → 팀 단위 컨벤션 합의 필요성 대두 → ESLint/Prettier 등 자동화 도구로 강제 → 코드 리뷰의 로직 집중 및 협업 비용 절감

## 5. Express.js GET 요청

**정의:** `app.get(경로, 핸들러)` 형태로 클라이언트의 조회 요청을 처리하는 Express의 라우팅 메서드

**등장 배경**
- HTTP, "서버 상태 비변경·데이터 조회" 의미의 GET 메서드 정의(안전성·멱등성 원칙)
- 순수 Node의 `req.method`/`req.url` 수동 파싱 방식의 번거로움 → 선언적 라우팅 문법 필요성

**핵심 요소**

| 요소 | 설명 | 예시 |
|---|---|---|
| req (request) | 클라이언트 요청 정보 객체 | `req.query`, `req.params` |
| 쿼리 스트링 | 조회 조건·필터링용 부가 데이터 | `/search?keyword=node` |
| 경로 파라미터 | 리소스 식별용 필수 데이터 | `/users/:id` |
| res (response) | 서버 응답 객체 | `res.send()`, `res.json()`, `res.status()` |

**설계 원칙**

| 원칙 | 의미 |
|---|---|
| 안전성(Safe) | GET 요청이 서버 상태를 변경하지 않음 |
| 멱등성(Idempotent) | 동일 요청 반복 시 결과 동일 |
| 리소스 식별 vs 조회 조건 | 경로 파라미터(필수) vs 쿼리 스트링(선택) 구분 기준 |

**실무에서의 형태**

| 사용처 | 설명 |
|---|---|
| 검색/필터/페이지네이션 | 쿼리 스트링 활용 (`/products?category=shoes&page=2`) |
| 특정 리소스 식별 | 경로 파라미터 활용 (`/users/42`) |
| 라우터 모듈화 | `express.Router()`로 파일 단위 라우트 분리 |
| 타입 변환 주의 | `req.params`/`req.query` 값은 항상 문자열, 명시적 변환 필요 |
| 보안 연계 | 검증 없는 값의 DB 쿼리 직접 사용 시 SQL Injection 위험 |

**인과관계 요약**
> HTTP의 GET 메서드 원칙(조회 전용) 확립 → 수동 라우팅 파싱의 번거로움 → Express의 선언적 라우팅 문법(`app.get`) 등장 → 리소스 식별(경로 파라미터)과 조회 조건(쿼리 스트링)의 역할 분화 → 사용자 입력값의 타입·보안 검증 필요성 → 이후 ORM·파라미터화 쿼리 등 보안 원칙과 연결

## 6. 핵심 요약 (인과관계)

**① Node.js**
- 언어 이원화 및 블로킹 I/O 비효율 → V8 + 비동기 I/O 결합 런타임 등장 → 싱글 스레드 기반 대량 동시 처리 실현 → JS 풀스택 생태계 형성

**② Express.js / package.json / PM2**
- http 모듈의 수동 라우팅 부담 → 선언적 프레임워크(Express) 등장
- → 외부 패키지 조합 개발 확산 → 의존성 관리 표준(package.json) 정착
- → 싱글 스레드 프로세스 종료 리스크 → 자동 재시작 도구(PM2) 등장

**③ Express.js 설치**
- Node 경량 코어 철학 → Express 별도 설치 필요
- → npm init/install 통한 의존성 선언 및 다운로드
- → package.json(의도)-package-lock.json(고정) 역할 분리 → 팀 환경 재현성 확보

**④ 코드 컨벤션**
- JS 문법의 유연성 → 개발자별 스타일 편차
- → 협업 시 diff 오염 및 리뷰 비효율 → 팀 단위 컨벤션 합의 필요
- → ESLint(품질)/Prettier(형식) 자동화 도구 도입 → 리뷰의 로직 집중화

**⑤ Express.js GET 요청**
- HTTP GET의 안전성·멱등성 원칙 확립 → 선언적 라우팅 문법(`app.get`) 등장
- → 리소스 식별(경로 파라미터)/조회 조건(쿼리 스트링) 역할 분화
- → 사용자 입력값의 타입 변환·검증 필요성 → 보안(SQL Injection 등) 이슈와 직결

**⑥ 종합 관계**
- Node.js(런타임) 기반 위에 Express.js(프레임워크) 구축 → package.json(의존성 관리)·PM2(프로세스 관리)로 개발·운영 인프라 완성
- 코드 컨벤션은 다수 개발자 협업의 커뮤니케이션 비용을 줄이는 장치로 전체 개발 프로세스에 수평적으로 적용
- Express의 GET 요청 처리 방식은 HTTP 스펙의 원칙(안전성·멱등성)을 프레임워크 레벨에서 구현한 사례이며, 이후 POST 요청·REST API 설계·보안 개념으로 확장 연결
