# 01. 웹 개념 & 클라이언트-서버 구조

> Web 1.0/2.0/3.0, JSON, 클라이언트-서버 구조, 프론트엔드/백엔드, HTTP

---

## 1. Web 1.0 → 2.0 → 3.0

| 구분 | 시기 | 핵심 특징 | 등장 배경 |
|---|---|---|---|
| Web 1.0 | 1990년대~2000년대 초 | 읽기 전용, 정적 페이지 | 종이 문서를 디지털로 옮기려는 목적 |
| Web 2.0 | 2000년대 중반~현재 주류 | 참여·생산, 실시간 상호작용(AJAX) | 브라우저 기술 발전 + 사용자 콘텐츠 생산 수요 |
| Web 3.0 | 진행 중 (개념적) | 탈중앙화(블록체인) / 시맨틱 웹 | Web 2.0의 데이터 독점 문제에 대한 반작용 |

**인과관계 요약**
> 종이 문서를 디지털화(1.0) → 브라우저 기술 발전 + 인터넷 인구 폭증으로 실시간 참여형 웹 필요(2.0) → 소수 플랫폼의 데이터 독점에 대한 반작용으로 분산·지능형 웹 논의(3.0)

## 2. JSON (JavaScript Object Notation)

**정의:** key-value 쌍으로 이루어진, 가볍고 사람이 읽기 쉬운 데이터 교환 형식

**등장 배경**
- Web 2.0에서 클라이언트-서버 간 실시간 데이터 통신 필요 증가
- 기존 표준이던 XML은 태그가 많아 무겁고 파싱이 번거로움
- 당시 모든 브라우저에는 자바 스크립트 엔진이 기본 탑재되어 있었음
- JavaScript 객체 문법을 그대로 재활용 → 가볍고 `JSON.parse()`로 즉시 변환 가능

**예시**
```json
{
  "name": "철수",
  "age": 20,
  "isStudent": true,
  "hobbies": ["축구", "독서"]
}
```

**실무에서의 형태**

| 사용처 | 설명 |
|---|---|
| REST API 요청/응답 바디 | 클라이언트 ↔ 서버 데이터 교환 |
| 설정 파일 | `package.json`, `tsconfig.json` 등 |
| NoSQL DB | MongoDB의 BSON 형식과 유사 |
| 프론트엔드 fetch | API 응답을 `.json()`으로 파싱 |

## 3. 클라이언트-서버 구조 / 클라이언트-서버 / 프론트엔드-백엔드

**등장 배경**
> 메인프레임(중앙 컴퓨터)이 모든 걸 처리하던 시절 → PC 보급으로 사용자 기기도 계산 능력이 생김 → 역할 분담("데이터는 중앙에, 화면은 각자")이 이득 → 클라이언트-서버 구조 등장

**핵심 정의**

| 용어 | 의미 |
|---|---|
| 클라이언트 (Client) | 요청(Request)을 보내는 주체 (브라우저, 앱) |
| 서버 (Server) | 요청을 받아 처리·응답(Response)하는 주체 |
| 프론트엔드 | 화면을 만드는 개발 영역 (보통 클라이언트에서 실행) |
| 백엔드 | 로직·데이터 처리를 만드는 개발 영역 (보통 서버에서 실행) |

> **주의:** 클라이언트/서버는 "통신 역할" 구분, 프론트엔드/백엔드는 "개발 영역" 구분 — 대부분 겹치지만 개념적으로 다름

**장점과 트레이드오프**

| 장점 | 트레이드오프 |
|---|---|
| 관심사 분리, 보안, 재사용성 | 서버 다운 시 클라이언트 간 통신 불가 (SPOF) → 서버 이중화로 보완 |

## 4. HTTP (HyperText Transfer Protocol)

**정의:** 클라이언트-서버가 데이터를 주고받기 위한 "요청-응답" 통신 규약

**3대 특징**

| 특징 | 의미 | 존재 이유 |
|---|---|---|
| 텍스트 기반 | 사람이 읽을 수 있는 형태 | 디버깅·표준화 용이 |
| 비연결성 (Connectionless) | 응답 후 연결 종료 | 서버 자원 절약 |
| 무상태 (Stateless) | 이전 요청을 기억하지 않음 | 대규모 동시 사용자 처리(확장성) |

**인과관계 요약**
> 서버가 수백만 클라이언트를 동시에 감당해야 함 → 일부러 Stateless/Connectionless하게 설계 → 로그인 유지 같은 게 불가능해지는 부작용 발생 → 쿠키/세션으로 애플리케이션 레벨에서 우회

**HTTP 메시지 예시**
GET /users/1 HTTP/1.1
Host: api.example.com
Accept: application/json
HTTP/1.1 200 OK
Content-Type: application/json
{ "id": 1, "name": "철수" }

**HTTP와 JSON의 관계**
> HTTP가 "봉투를 주고받는 규칙"이라면, JSON은 "그 봉투 안에 든 편지"다. 즉 서로 다른 층위의 개념.

## 5. 핵심 요약 (인과관계)

**① Web 1.0 → 2.0 → 3.0**
- 종이 문서의 디지털화 목적 ⇒ 읽기 전용 정적 페이지 (1.0)
- → 브라우저 기술(JS/AJAX) 발전 + 인터넷 인구 폭증 ⇒ 참여·실시간 소통형 웹 필요 (2.0)
- → 소수 거대 플랫폼의 데이터 독점 심화 ⇒ 소유권 분산(블록체인) / 웹 지능화(시맨틱) 반작용 (3.0, 진행 중)

**② JSON**
- Web 2.0의 실시간 데이터 통신 수요 발생
- → 기존 표준 XML의 무거운 태그 구조 및 파싱 번거로움 → 한계 노출
- → JavaScript 객체 문법의 데이터 형식 재활용 → 경량화 실현
- ⇒ 언어 무관 데이터 교환의 사실상 표준 정착

**③ 클라이언트-서버 구조**
- 메인프레임 중심의 중앙 집중 처리 방식
- → PC 보급에 따른 사용자 기기 연산 능력 확보
- → "데이터는 중앙, 화면은 각자" 역할 분담 → 보안·확장성 확보
- ※ 트레이드오프: 서버 장애 시 클라이언트 간 통신 단절(SPOF) → 서버 이중화로 보완

**④ 클라이언트/서버 vs 프론트엔드/백엔드**
- 클라이언트/서버 = 통신 역할 구분 (요청 주체 / 응답 주체)
- 프론트엔드/백엔드 = 개발 영역 구분 (화면 담당 / 로직·데이터 담당)
- ※ 대응 관계: 프론트엔드 ≈ 클라이언트, 백엔드 ≈ 서버 (단, 풀스택 프레임워크 확산으로 경계 유연화 추세)

**⑤ HTTP**
- 이기종 컴퓨터 간 데이터 교환을 위한 공통 규칙(프로토콜) 필요성 대두
- → "요청-응답" 구조의 HTTP 확립
- → 대규모 동시 사용자 처리 목적 ⇒ 의도적 Stateless(무상태)·Connectionless(비연결) 설계 채택
- ※ 부작용: 로그인 상태 유지 등 연속성 확보 불가 → 쿠키/세션(애플리케이션 레벨 장치)으로 우회 구현

**⑥ 종합 관계**
- HTTP = 통신 규칙(프로토콜) / JSON = 규칙을 통해 오가는 데이터 형식(포맷) → 상호 층위 상이
- Web 2.0의 실시간 통신 요구 → 클라이언트-서버 구조 확립 → 역할별 개발 영역(프론트/백엔드) 분화 → HTTP 규칙 하에 JSON 데이터 교환, 이 전 과정이 하나의 인과 사슬로 연결
